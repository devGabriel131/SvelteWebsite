# Database schema

**Implemented:** PostgreSQL roster/editing, canonical account-to-student identity, invitation onboarding, Better Auth storage, bootcamp registration/documents/payments, and game-history tables/views. **Not integrated:** game persistence, global student-dashboard lifecycle/profile gating, public leaderboards, or unfinished-round resume. Public learning tools still use page-memory state; a stored profile or valid session does not imply every future student-data contract is implemented.

Use standard PostgreSQL with Drizzle ORM, postgres.js, and append-only Drizzle SQL/snapshots/journal. Browser components never import the database. `DATABASE_URL` is private, runtime-read, and optional until a database operation is requested. Application connections are lazy; standalone tools use `src/lib/server/db/connection.ts`. See [README setup and commands](../README.md#local-postgresql).

## Student identity and profile

`src/lib/server/db/schema.ts` owns `students`, `student_accounts`, `student_invitations`, and demonstration subject scores. Better Auth separately owns login identities and credentials in `auth-schema.ts`. Game history references the stable student UUID, not an email or auth ID. Associations are server-owned: matching emails never establishes identity.

### Students

| Field | Current representation and contract |
| --- | --- |
| `id` | Stable UUID primary key, generated by default. |
| `first_name`, `last_name` | Separate required nonblank text; preserve accents and compound names rather than splitting a full name. |
| `email` | Required enrollment address; unique `lower(btrim(email))` index across all profiles, including inactive/invited/unlinked students. Entered casing is retained by storage; server writes trim/validate, and admin edits normalize to lowercase. Input whitespace is rejected; dots and plus-addresses are not collapsed. |
| `date_of_birth` | Nullable finite, nonfuture calendar date. Staff may leave it empty; invitation completion requires it. Calculate age for the relevant date, not a stored current age. |
| `gender` | Nullable `male`/`female`; invitation completion requires a supported choice. Never infer the IST sex baseline from profile gender. |
| `class_type` | Required `basic`/`regular`, independent of authorization role. No class-specific feature system is implemented. |
| `status` | Sole lifecycle field: required `active`/`inactive`/`invited`, default `active`, checked by `students_status_valid`. Imports explicitly start as `invited`. |
| `created_at`, `updated_at` | Required timezone timestamps. The `0001` PostgreSQL `BEFORE UPDATE` trigger uses `clock_timestamp()` for ORM and raw SQL changes, including repeated changes in one transaction. |

The database permits incomplete staff-entered and invited profiles. A canonical association does **not** require birth date/gender to be populated: imported accounts exist before acceptance. There is no editable registration/profile-complete flag. Class changes preserve the student ID and history; no course/lesson/teacher schema is implied.

### Canonical account association

`student_accounts` is the one identity owner used by invitations/enrollment, roster `hasAccount`, linked-email protection, bootcamp eligibility, and document authorization.

| Field | Contract |
| --- | --- |
| `user_id` | Text primary key referencing `auth_user.id` with `ON DELETE RESTRICT`; an account links to at most one student. |
| `student_id` | Nonnull unique UUID referencing `students.id` with `ON DELETE RESTRICT`; a student links to at most one account. |
| `linked_by` | Nullable text referencing the linking auth actor with `ON DELETE RESTRICT`. |
| `created_at` | Nullable timezone timestamp, retaining its `now()` insertion default. |

The named `student_accounts_link_provenance` CHECK requires `(linked_by IS NULL) = (created_at IS NULL)`. Both null means unknown historical provenance, not an invented operator/time. New imports supply both the admin actor and timestamp. Existing legacy association provenance is preserved. Restrictive links must be deliberately removed before deleting either identity/profile or a referenced linking actor; there is no public unlink/reassociation endpoint.

### Identity and lifecycle cutover

Apply `0011_student_accounts.sql`, then `0012_students_status_only.sql`, with the matching application version; do not deploy mixed old/new binaries. The installed Drizzle runner supplies their transaction. Migration history remains immutable.

- `0011` locks the legacy profile/association tables, checks **both** conflicts (one student linked to different users, or one user linked to different students) **before DDL/backfill**, then renames the association table/constraints. It preserves legacy rows/actor/time, inserts missing invitation associations with explicit null provenance, verifies all old profile links, and only then removes the old profile identity column. A conflict raises SQLSTATE `23514`: `Conflicting student account links. Resolve associations before rerunning migrations.` No email-based repair or silent conflict suppression occurs; rollback retains both original representations for operator correction.
- `0012` locks students and checks the old activity projection against `status = 'active'` before removing that projection, its trigger/function, and consistency constraint. A mismatch raises SQLSTATE `23514`: `Inconsistent student lifecycle state. Resolve rows before rerunning migrations.` Status default/non-null/allowed-value constraints remain. Current schema has neither the old activity column/trigger nor the profile auth-ID column.

## Admin student editing and lifecycle

Verified-admin loads read the roster and optional subject scores with a left join, so students without scores remain visible and missing scores display as unavailable, never zero. `hasAccount` is derived from the canonical association without exposing auth IDs. The root admin load acquires its database once and returns a 200-row invitation page with lookahead pagination.

The editor persists first/last names, email, optional birth date/gender, class, status, and all four integer demonstration scores. All four blank scores remove the optional score row; partial sets are rejected. Profile/score changes share one transaction. Current-session admin and exact Origin checks run before body/dependency access; the edit POST is private/no-store. Forms cannot change IDs, associations, timestamps, fixture markers, or credentials. Validation/duplicate/missing/storage errors do not expose SQL details.

Unlinked roster emails remain editable. Any canonical-linked student's login email is read-only: the service locks the student first, then checks the association and rejects an email change. It never independently changes Better Auth addresses. `inactive` and `invited` are nonactive for bootcamp/payment/report eligibility; lifecycle changes preserve history. This is **not** a global sign-in/public-tool gate.

### Admin subject-score fixtures

`0007_student_subject_scores.sql` provides one optional demonstration row per student. `student_id` is the primary key and an `ON DELETE CASCADE` FK; AR, PC, WK, MK are required integers in 0–100, and `is_fixture` must be true. There is no overall score or roster progress calculation, validated ASVAB scoring, official percentile, or exam-source contract.

`bun run db:seed:subject-scores` requires all 100 exact `fake.student.001..100@example.test` addresses with `Test`/`(Test)` surnames. It inserts arbitrary fictional values, preserves existing students/scores, and creates no accounts. Real assessment storage needs separately agreed source/scoring rules.

## Authentication and invitations

Better Auth tables are `auth_user`, `auth_account`, `auth_session`, `auth_verification`, and `auth_rate_limit`; auth IDs are text, separate from roster UUIDs. `0004` creates them and `0005` adds the server-controlled student/admin role, defaulting existing accounts to student. Credentials, sessions, Origin/IP/rate-limit policy, production provisioning, and the guarded local-admin exception have one owner: [authentication](authentication.md).

`0010_student_invitations.sql` adds one current invitation per student. Current `student_invitations` stores the student PK/cascading FK, unique SHA-256 token digest, recipient email, `en`/`es` language, expiry/acceptance, `pending`/`sending`/`sent`/`failed` delivery state, test-mode snapshot, send/attempt times, creator (`ON DELETE RESTRICT`), and creation/update times. PINs and raw workbooks are not stored in this table.

Import provisions auth identity/hashed credential, an `invited` student, canonical association with known provenance, and invitation in one transaction. Acceptance locks profile → invitation → auth identity, validates the unchanged association/email and token, then completes profile, verifies login email, activates status, and consumes the invitation atomically. There is no second bootcamp association to create. Email acknowledgment and enrollment acceptance are independent states. Token lifetime, explicit resend rotation/cooldown, intake limits, and mail behavior belong to [student import and invitations](student-import.md).

## Bootcamp storage

`bootcamp-schema.ts` owns events, registrations, immutable signed snapshots/PDF bytes and hashes, durable backup status/reserved IDs, and payment attempts/encrypted capabilities. Restrictive FKs and immutable association/evidence triggers preserve legal/payment history. `0009` enforces one open event with its named partial unique index; canonical account associations belong to roster schema, not a bootcamp-only table.

Registration locks and feature-specific active/age/event/proof checks, document SQL authorization before loading bytes, durable Drive recovery, and event-specific reporting belong to [bootcamps](bootcamps.md). Payment wire evidence, globally unique settlement IDs, authorization-intent fencing, encryption, and reconciliation belong to [ATH bootcamps](ath-bootcamps.md). No mutable browser-supplied paid counter or automatic history deletion is permitted.

## Implemented game-history

`game-schema.ts` defines `0002_game_history.sql` tables; `views.ts` owns derived progress/ranking views. Constant-only schema imports use frequency `rules.ts`, not the scheduler/catalog. `0003_frequency_catalog.sql` records the initial `frequency-v1` membership of all 1,001 bundled item UUIDs/ranks; it contains no student data and is separate from opt-in roster seeding.

| Table | Implemented contract |
| --- | --- |
| `game_attempts` | Stable UUID, restrictive student FK, `speed_math`/`frequency`, nonblank rules version, finite start, nullable finite end not before start, creation time. |
| `speed_math_results` | One result per attempt; operation and 5/10/15-minute duration constraints; explicit nonnegative correct/incorrect counts; nullable finite `verified_at`. Composite FK requires a math attempt. |
| `vocabulary_items` | Permanent UUID catalog from `words.json`, independent of rank/spelling; no generated replacement IDs or duplicate translation store. |
| `vocabulary_pools` / `vocabulary_pool_items` | Versioned pool IDs and immutable published membership/ranks, unique within each pool. Change denominator/order with a new pool ID/migration; retain old snapshots. |
| `vocabulary_rounds` | One frequency attempt bound to a pool; composite FK rejects wrong-game attempts. |
| `vocabulary_responses` | Attempt/card position (1–25) PK, pool/member FKs, `correct`/`incorrect`/`skipped`, finite answer time, creation time. Repeated items at different positions are valid; no raw answer text or copied student identity. |

Content/translations stay in bundled JSON. Future grading must version meaningful content/scoring changes rather than reinterpret historical outcomes. Response history is authoritative; views are not editable counters/caches:

- `student_word_progress`: lifetime correct/incorrect/skipped counts, latest time/outcome by student/stable item. Missing rows mean zero; equal times use descending attempt ID/card position. Counts follow items across pool versions, not unrelated future games.
- `vocabulary_round_progress`: accepted response/outcome counts for every round, including zero-response and ended partial rounds. Exactly 25 completes a round; an end timestamp does not fabricate completion.
- `student_vocabulary_completeness`: explicit full-pool denominator including unpracticed items; practice coverage, first successful coverage, full passes (minimum correct count), current pass and current-pass completion (`correct_count > full_passes`). Empty pools have zero counts/current pass 1. Preserve historical counts when showing a new denominator; these are completion, not permanent mastery.
- `speed_math_verified_bests`: one verified full-duration best per student/operation/duration/rules version, most correct then fewest incorrect. End must equal the deadline; verification must be at/after it. Early, partial, late/unclamped, and unverified attempts stay in history but cannot compete. Equivalent bests choose earliest end then ascending UUID.
- `speed_math_leaderboard_entries`: all-time shared `RANK()` by correct/incorrect within each category (`1, 1, 3` ties), one best per student. Supporting accuracy/rate statistics are not extra tie-break scores. Views expose IDs, not public names, and do not filter current status.

No percentages, mastery booleans, or mutable pass counters are stored. Derivation avoids summary synchronization/rebuild races; add a transactionally maintained, rebuildable cache only if measured history volume warrants it. All game/history relationships restrict deletion; deactivation retains existing attempts/progress.

## Pending integrations and decisions

These requirements do not assert completed behavior or authorize a new global route gate:

- **Game persistence and trust:** resolve canonical student identity server-side, check current `status`, grade expected answers/cards and control timing, set verification server-side, and write attempt/results or round/responses transactionally. Clients must not choose trusted student IDs, outcomes, counters, rules, or `verified_at`. Reuse stable attempt/card retry identities; unique keys alone cannot distinguish identical retries from conflicting payloads. A verification timestamp is not proof of grading.
- **Lifecycle/profile access:** broader protected dashboard/history access must check current state on every read/write, including existing sessions, not merely hide navigation or deny new logins. Inactive profiles/history must survive and reactivation reuse them. An active roster entry alone is not enrollment; invitations cannot reactivate an inactive profile. Public tools remain public today. Define editing permissions for student-owned versus server-controlled fields before exposing more profile writes.
- **Email correction and recovery:** linked enrollment/login addresses cannot be independently edited. Coordinated post-registration email change/correction and safe credential reset/recovery remain undecided; current invitations use staff-issued credentials and seven-day explicit-rotation links, not proposed replacement invitation systems.
- **Enrollment ages:** nonfuture real DOB and the two offered gender values are required at acceptance; supported general enrollment age limits remain undecided. Bootcamp's existing 21+ rule is separate. Do not impose a database completeness CHECK that forbids invited linked profiles.
- **Learning policy:** adaptive rounds already use 25 accepted attempts, lowest-correct-count eligibility, missed/skipped retry priority, recalculation after each response, and repeats when alternatives run out. Immediate repetition is avoided when possible. Current `1 + incorrectCount + skippedCount` weighting remains open for product agreement; skipped and incorrect are distinct outcomes with equal retry weight. Save accepted progress individually when persistence is connected; leaving early should retain it without claiming unfinished-round resume.
- **Leaderboard presentation:** all-time, operation/duration/rules categories, full-duration eligibility, one best per student, and shared ranks are agreed. Audience, displayed names, and inactive-student visibility remain undecided; no public leaderboard is implemented.
- **Resume and retention:** partial storage does not imply resumable rounds. Round resume, deletion/retention, and whether other vocabulary games share progress require decisions. Keep authoritative response history if a cache is added; no permanent mastery threshold is approved.
- **Future IST history:** saving sensitive fitness assessments is unapproved. If requested, decide access/retention first and retain inputs, assessment date/age, explicit sex baseline, rules version, and immutable historical meaning independently of later profile/threshold changes.

## Local tooling and safety

`bun run db:seed` inserts only three stable-ID `@example.test` profiles, no credentials, and never overwrites existing records. All seeds and opted-in PostgreSQL suites use `openLocalDatabase(databaseUrl, purpose)` from `scripts/db/local-target.ts`: reject production/Railway, remote hosts, connection-option overrides, and unknown database/user/port combinations before connection, then verify actual database and session user before writes. Never tunnel allowed local ports to a hosted database. Identity verification failure closes the connection without replacing its original error, even if close fails. Seeds close verified clients in `finally`; tests use scoped fixtures/rolled-back transactions.

`compose.test.yaml` is the disposable PostgreSQL 18 target at `127.0.0.1:5434`, separate from persistent development storage at port 5433. `db:test` explicitly selects its public test-only URL and uses Bun substring discovery `tests/database`, so new database suites need no filename list. Normal tests skip PostgreSQL suites without `TEST_DATABASE_URL`; an opted-in unreachable database fails rather than skips. Migration tests execute committed SQL, including conflict rollback/provenance/uniqueness/restrictive-FK cutover contracts, without mutating committed application rows. See [README validation](../README.md#validation) and [isolated database tests](../README.md#isolated-database-tests). Never seed production or create mock identity requirements for ordinary public development.
